Улыбин А. А., группа ПИбд-42. Дисциплина «Конструирование программного обеспечения».

## Цель работы

Организовать управление исходным кодом web-сервиса генерации отчётов на основе
логов web-сервера, автоматизировать контроль качества, тестирование, сборку
и измерение показателей на этапах разработки.

## Хостинг и структура репозитория

Для размещения проекта выбран GitHub. Имя репозитория — web-log-reports.
Автоматизация выполняется средствами GitHub Actions; изменения рассматриваются
и сливаются через Pull Request. Инкрементная модель и календарные этапы
лабораторной 3, а также архитектура лабораторной 4 сохраняются.

Исходный код находится в src/web_log_reports, модульные и интеграционные тесты —
в tests/unit и tests/integration, проверка коммитов и сбор метрик — в scripts.
Каталог docs содержит описание архитектуры, порядок работы и снимки метрик.
Файлы pyproject.toml, README.md, CHANGELOG.md и .gitignore находятся в корне.
Workflow размещён в .github/workflows/ci.yml, шаблон PR — в .github/pull_request_template.md.

URL репозитория и снимок его страницы фиксируются после создания проекта.

## Управление исходным кодом

Принята стратегия GitHub Flow: main содержит проверенное состояние проекта,
короткие ветки feature/*, fix/* и docs/* соответствуют отдельным задачам.
Изменения проходят через PR с описанием задачи YouGile, просмотром diff,
автоматическими проверками и слиянием после их успеха.

Коммиты оформляются по Conventional Commits с ограничением заголовка до
100 символов. Пример: `feat(parser): parse access log records`.
Локальная проверка выполняется commit-msg hook, подключённым через
`git config core.hooksPath .githooks`. Скрипт check_commits.py повторяет проверку
в CI. Автоматические merge-коммиты исключены из проверки; squash в принятой
схеме отключается, чтобы сохранять отдельные проверенные коммиты.

Для main на GitHub задаются требование PR, обязательные проверки commit-policy,
lint, tests-and-metrics и build, актуальность ветки относительно main,
разрешение обсуждений и применение ограничений к владельцу репозитория.
Обязательное одобрение второго участника для индивидуального проекта не задаётся.
Работа защиты подтверждается PR с неуспешным lint и заблокированным слиянием.

## Автоматизация GitHub Actions

Workflow выполняется при push веток, создании тегов, изменении PR в main
и по ручному запуску. Для PR проверяется пробное слияние с main.

| Job | Проверки и результат |
| --- | --- |
| commit-policy | Проверка заголовков обычных коммитов |
| lint | Статический анализ Ruff и проверка форматирования |
| tests-and-metrics | pytest, покрытие строк и ветвей, JUnit, Radon, metrics.json |
| build | Wheel и sdist после успеха трёх предыдущих jobs |

Первые три jobs выполняются параллельно. Падение любой обязательной проверки
препятствует сборке. Сбор метрик и сохранение доступных отчётов выполняются
также при неуспешном тестировании; исходный сбой не скрывается.

Минимальное совокупное покрытие строк и ветвей установлено в 80 процентов.
Артефакт quality-reports содержит Coverage XML/HTML, JUnit XML, Ruff JSON,
Radon JSON и сводный metrics.json. Артефакт dist содержит wheel и sdist.
Метрики также выводятся в Summary запуска. Артефакты сохраняются на 30 дней.
Автоматическое развёртывание является опциональным пунктом задания и не включено.

## Автоматически собираемые метрики

| Показатель | Источник |
| --- | --- |
| Число замечаний линтера | Количество диагностик Ruff JSON |
| Средняя цикломатическая сложность | Radon, функции и методы приложения |
| Максимальная цикломатическая сложность | Radon |
| Покрытие строк | Coverage XML, покрытые строки / исполняемые строки |
| Покрытие ветвей | Coverage XML, покрытые переходы / возможные переходы |
| Passed, failed, errors, skipped | JUnit XML |
| Время тестирования | Сумма времени testsuite в JUnit XML |

Снимок содержит дату измерения, SHA проверенной версии, ref и ссылку на запуск
GitHub Actions. При локальном запуске ссылка отсутствует, состояние обозначается
как local-uncommitted. Отсутствующий исходный отчёт отмечается ошибкой;
показатели не подменяются нулями. Диагностики линтера не приравниваются
к подтверждённым дефектам программы.

Область покрытия и сложности — исходники приложения. Ruff проверяет src,
tests и scripts, а число тестов и время относятся ко всему набору тестов.

## Создание релиза

После успешного слияния и проверки main создаётся аннотированный тег v0.1.0.

добавляются изменения из CHANGELOG и файлы wheel/sdist из dist-артефакта.
