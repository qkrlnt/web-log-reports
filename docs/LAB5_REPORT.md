# Лабораторная работа 5

Управление исходным кодом и отслеживание метрик

## 1 Цель и объект работы

Цель работы — организовать хранение исходного кода, правила внесения изменений, автоматический контроль качества, сборку и измерение метрик учебного проекта. Объект работы — web-сервис формирования PDF-отчётов по журналам web-сервера. Модель жизненного цикла и этапы приняты из лабораторной 3, архитектура — из лабораторной 4.

Текущая версия 0.1.0 реализует минимальный прототип: разбор записей CLF/Combined, приём пакета строк через FastAPI и расчёт общей статистики. Данные хранятся в памяти. Fluent Bit, SQLite, расширенная аналитика, PDF и интерфейс относятся к дальнейшей реализации. Показатели качества ниже характеризуют именно прототип.

## 2 Хостинг и структура репозитория

Для размещения выбран GitHub, для автоматизации — GitHub Actions. Репозиторий: [qkrlnt/web-log-reports](https://github.com/qkrlnt/web-log-reports). Основная ветка — main; файлы настройки и документация хранятся вместе с кодом.

| Каталог или файл | Назначение |

Виртуальное окружение, временные отчёты, сборки, реальные журналы и .env исключены через .gitignore. Персональные сведения удалены из опубликованных веток и тега; новые коммиты используют псевдоним и GitHub noreply email.

## 3 Правила фиксации изменений

Используется формат Conventional Commits: тип(область): описание. Область необязательна; заголовок ограничен 100 символами. Допустимые типы: feat, fix, docs, style, refactor, perf, test, build, ci, chore, revert.

Примеры: `feat(parser): parse access log records`, `fix(api): reject invalid log batch`, `docs: сохранить метрики версии 0.1.0`.

Локальная проверка подключается командой `git config core.hooksPath .githooks`. Hook вызывает scripts/check_commits.py. Аналогичная проверка выполняется в CI, поэтому правила сохраняются независимо от настройки рабочего компьютера. Автоматические merge-коммиты пропускаются. Сообщение `update` не соответствует правилам: в нём отсутствуют тип и разделитель. Заголовки проверяются модульными тестами.

## 4 Ветвление и слияние

Принята стратегия GitHub Flow: main содержит основную версию, изменения выполняются в коротких ветках и рассматриваются через Pull Request. Примеры имён: feature/log-ingestion, fix/invalid-log-date, docs/add-project-goals. В описании PR указываются назначение изменения и связанная задача при её наличии.

Ветка docs/add-project-goals использована для изменения README. [Pull Request 1](https://github.com/qkrlnt/web-log-reports/pull/1) слит 18.11.2026 через merge commit. После очистки персональных данных история переписана: текущие коммиты — baa662e, 55fb280 и cafb0bb. Связи ветвления и слияния сохранены, но старые идентификаторы в историческом PR отличаются от новых.

Задание требует защиту основной ветки, запрещающую слияние без проверок. Для main предусмотрены обязательный PR и четыре обязательные проверки: commit-policy, lint, tests-and-metrics, build. Дополнительно требуются актуальность ветки, завершение обсуждений и применение правил к владельцу. Одобрение второго участника для индивидуального проекта не устанавливается.

На дату подготовки отчёта, 18.11.2026, репозиторий приватный. Защита приватной ветки на GitHub Free недоступна. Поэтому текущая конфигурация CI выполняет проверки и блокирует сборку при их сбое, но сама по себе не обеспечивает серверный запрет слияния. Перед демонстрацией необходимо обеспечить доступность защиты и проверить её применение либо согласовать ограничение с преподавателем.

## 5 Автоматизация контроля качества

Workflow CI запускается при push веток и тегов, изменении PR в main и вручную через workflow_dispatch. В PR проверяется пробное слияние с основной веткой; политика коммитов применяется к исходным коммитам PR.

Первые три jobs независимы. Job build выполняется только после успеха всех трёх. Порог совокупного покрытия строк и ветвей для pytest-cov равен 80 процентам. Метрики и доступные отчёты сохраняются также при падении тестов; ошибка тестов при этом остаётся ошибкой job. Автоматическое развёртывание в задании опционально.

Контрольный запуск для тега v0.1.0 от 18.11.2026 выполнен вручную и завершён успешно. Его событие — workflow_dispatch; он не выдаётся за автоматический запуск по push.

| Job | Действия | Результат |
| --- | --- | --- |
| commit-policy | Проверка сообщений коммитов | Success |
| lint | Ruff check и Ruff format --check | Success |
| tests-and-metrics | pytest, покрытие, JUnit, Radon и metrics.json | Success |
| build | Сборка wheel и sdist | Success |

Артефакт quality-reports содержит metrics.json, coverage.xml, junit.xml, ruff.json, complexity.json и HTML-отчёт покрытия. Артефакт dist содержит установочный пакет и архив исходников. В проекте срок хранения артефактов — 30 дней. JSON также выводится в Summary запуска.
